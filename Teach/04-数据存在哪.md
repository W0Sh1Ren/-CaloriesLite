# 04 · 数据存在哪

这一章讲**数据流的前一半**：记录怎么存进去、怎么读出来、为什么不会丢。

读完你会知道：数据存哪个文件、格式是什么、为什么不上传、以及哪些做法是**错的**。

---

## 一、先想清楚：数据有几种

App 里的数据分三类，**存法完全不同**：

| 类型 | 例子 | 存哪 | 什么时候丢 |
|---|---|---|---|
| **持久数据** | 饮食记录、体重、个人档案、API Key | **手机的文件** | 卸载 App 才丢 |
| **临时数据** | 「刚识别完还没确认的结果」 | **内存** | App 关掉就丢 |
| **界面状态** | 「当前展开了哪一餐」 | **内存** | 页面离开就丢 |

**新手最容易犯的错**：把该持久化的东西放在内存里。
结果用户记了一堆数据，重启 App 全没了。

本项目的原则：

> **只要是用户「输入过」的东西，一律持久化。**
> 只要是「看一眼就过去」的状态，放内存。

---

## 二、持久数据：用 preferences（键值存储）

### 什么是键值存储

想象一个**抽屉柜**，每个抽屉有个标签：

```
┌─────────────────────────────────────┐
│ 标签                       抽屉内容  │
├─────────────────────────────────────┤
│ "food_day_2026-10-05"  →  [{...},{...}] │
│ "food_day_2026-10-04"  →  [{...}]       │
│ "food_day_index"       →  ["2026-10-05", …] │
│ "profile"              →  {身高:188, …}  │
│ "ai_config"            →  {apiKey: "...", …} │
│ "weight_list"          →  [{...}]        │
└─────────────────────────────────────┘
```

**你给一个标签（键），它给你对应的内容（值）。** 就这么简单。

鸿蒙里这个抽屉柜叫 **`preferences`**，属于 `@kit.ArkData`。

### 为什么不用数据库

| | 键值存储 | 数据库（SQLite 等） |
|---|---|---|
| 适合 | 数据量小、按固定标签取 | 数据量大、要复杂查询 |
| 用法 | `存(键, 值)` / `读(键)` | 写 SQL 语句 |
| 本项目 | ✅ 用了 | ❌ 没用 |

本项目的规模：**一天一条记录，一年 365 条**。
这种量级用数据库是「用大炮打蚊子」——多引入一层复杂度，没有收益。

### 值只能存「简单类型」

`preferences` 只支持：

```
字符串     "红烧肉"
数字       315
布尔       true / false
字符串数组  ["a", "b"]
```

**不能直接存对象**。所以要存一条饮食记录时，得先转成**字符串**：

```ts
// 存：对象 → 文字
Store.put('food_day_2026-10-05', JSON.stringify(records));

// 读：文字 → 对象
const records = JSON.parse(Store.getString('food_day_2026-10-05', '[]'));
```

`JSON.stringify` = 把对象压成一段文字
`JSON.parse` = 把文字还原成对象

**这是本项目的核心手法**：所有复杂结构都转成 JSON 字符串存。

## 三、`Store.ets`：给抽屉柜套一层壳

项目没有直接用 `preferences`，而是包了一层 `common\Store.ets`。

**为什么要包**：直接用的写法很长很啰嗦：

```ts
// 直接用的样子（示意）
const prefs = await preferences.getPreferences(context, { name: 'xxx' });
await prefs.put('key', 'value');
await prefs.flush();
const v = await prefs.get('key', 'default');
```

包成 `Store` 之后：

```ts
Store.put('key', 'value');              // 存
const v = Store.getString('key', '');   // 读
```

**好处**：

1. **短** —— 调用处一行搞定
2. **统一处理错误** —— 出错在 `Store` 里记日志，不用每处都写
3. **提供兜底** —— 读不到时返回默认值，不会崩
4. **同步接口** —— `preferences` 原生是异步的，用 `getSync` 系列包成同步，
   页面代码就不用到处 `await`

### 一个必须知道的设计：同步写 + 异步落盘

```ts
static put(key: string, value: string | number | boolean): void {
  Store.prefs.putSync(key, value);        // ① 先写内存（立刻生效）
  Store.prefs.flush().catch(...);         // ② 再落盘（异步，不等它）
}
```

**为什么不等落盘完成**：

如果每次保存都等磁盘写入（可能十几毫秒），用户点「保存」时会感觉卡顿。
所以**先写内存（立刻能读回来）+ 后台慢慢落盘**。

**代价**：App 在落盘完成前被杀掉，这次修改会丢。
但实际中这个窗口只有几毫秒，可以接受。

> **这个设计后来引发过一个 bug**，见第 7 章「跨进程缓存」那节。

## 四、记录具体怎么存：一天一个键

这是 `service\FoodRepo.ets` 的核心设计，**值得单独讲**。

### 存储结构

```ts
const KEY_INDEX = 'food_day_index';   // 索引：哪些天有数据
const PREFIX_DAY = 'food_day_';       // 每天的记录：food_day_2026-10-05
```

实际存进去是这样：

```
"food_day_index"        →  ["2026-10-05", "2026-10-04", "2026-10-01"]

"food_day_2026-10-05"   →  [
                              {"id":"m3k2-8a","name":"红烧肉","grams":90,"kcal":315,…},
                              {"id":"m3k2-9b","name":"米饭","grams":239,"kcal":280,…}
                           ]

"food_day_2026-10-04"   →  [ … ]
```

### 为什么「一天一个键」而不是「一个大列表」

假设所有记录存在一个键里：

```ts
'food_all' → [第1条, 第2条, …… 第 3000 条]
```

问题：

| 问题 | 说明 |
|---|---|
| **每次都要读全部** | 只想看今天吃了什么，却要把 3000 条都读出来再筛 |
| **写放大** | 加一条记录，要把 3000 条全部重新写一遍 |
| **容易损坏** | 一个键存太多，写一半失败可能全丢 |

改成「一天一个键」后：

| 好处 | 说明 |
|---|---|
| 读某天 = 读一个键 | 快，且数据量恒定 |
| 加一条 = 只重写那一天 | 代价小 |
| 一天的损坏不影响其他天 | 安全性好 |

**这是很典型的「按查询方式设计存储结构」**——
先想清楚「我会怎么用这些数据」，再决定怎么存。

### 那为什么还要一个索引键

因为 `preferences` **不能枚举所有键**（不知道有哪些 `food_day_xxx` 存在）。

日历要显示「哪些天有记录」，就必须知道这个列表。所以额外维护一个：

```
"food_day_index" → ["2026-10-05", "2026-10-04", …]
```

**索引和真实数据必须同步维护**，看这段代码：

```ts
static saveDay(dayKey: string, records: FoodRecord[]): void {
  Store.put(PREFIX_DAY + dayKey, JSON.stringify(records));
  FoodRepo.indexSync(dayKey, records.length);   // ← 一定要同步！
}

/** 某天没有记录时把它移出索引，保持日历干净 */
private static indexSync(day: string, count: number): void {
  if (count > 0) {
    FoodRepo.indexAdd(day);
    return;
  }
  // 记录被删光了，索引里也要去掉
  const days: string[] = FoodRepo.indexRead().filter((d: string) => d !== day);
  FoodRepo.indexWrite(days);
}
```

> **如果不同步会怎样**：删光某天的记录后索引还在，
> 日历上那天还亮着，点进去却是空的。这种「索引和数据不一致」是
> 维护索引方案的**固有代价**——必须每次改动都记得同步。

## 五、增删改查：Repo 层的四个动作

`FoodRepo` 提供的方法，看名字就知道干什么：

| 方法 | 作用 | 关键点 |
|---|---|---|
| `loadDay(dayKey)` | 读某天全部记录 | 返回按时间正序排好的数组 |
| `add(record)` | 加一条 | 内部 = 读出整天 → 追加 → 写回 |
| `addMany(records)` | 批量加 | 一次识别出多道菜时用 |
| `remove(dayKey, id)` | 删一条 | 按 id 过滤掉 |
| `update(record)` | 改一条 | 按 id 覆盖 |
| `saveDay(dayKey, records)` | 整天覆写 | **最底层的方法**，其他都是它的组合 |

### 为什么「加一条」要「读出整天再写回」

```ts
static add(record: FoodRecord): void {
  const day: string = record.dayKey;
  const list: FoodRecord[] = FoodRepo.loadDay(day);   // ① 读整天
  list.push(record);                                  // ② 追加
  FoodRepo.saveDay(day, list);                        // ③ 写回整天
}
```

因为 `preferences` **不支持「往一个数组里追加一项」**——
只能整个值覆盖。所以要自己读出→改→写回。

这在数据量小时完全没问题（一天最多几十条）。

### 一个真实踩过的坑：`addMany` 不能用来改

代码里有一句注释很关键：

```ts
/** 批量新增（一次拍照识别出多道菜） */
```

**`addMany` 是纯粹的追加**，它不检查 id 是否已存在。

所以如果「编辑一条记录」时误用了 `addMany`，会变成**多出一条**而不是替换。
改记录必须用 `update`：

```ts
/** 更新一条记录（按 id 覆盖） */
static update(record: FoodRecord): void {
  // …
  if (r.id === record.id) {
    next.push(record);      // 找到同 id 的，替换掉
    replaced = true;
  }
  // …
  if (!replaced) {
    next.push(record);      // 没找到就追加（容错）
  }
}
```

> **教训**：「新增」和「更新」是两个不同的语义，
> 哪怕实现相似也**不要混用**。混用出的 bug 往往在编辑场景才暴露，
> 而那时你已经忘了当初为什么这么写。

## 六、老数据的兼容：为什么要写这么多判断

看 `loadDay` 里这段：

```ts
// 兼容两种历史写法：直接是数组，或 { records: [...] }
let items: JsonMap[] = [];
const direct: JsonMap[] = parseArray(raw);
if (direct.length > 0) {
  items = direct;
} else {
  const wrapped: JsonMap | null = parseObject(raw);
  if (wrapped !== null) {
    const inner: Object | undefined = wrapped['records'];
    // …
  }
}
```

**为什么**：项目早期存的是 `{ records: [...] }`，后来简化成直接存数组。
但**用户手机上还有旧格式的数据**，不能直接改代码就不管了。

所以读的时候要**两种都能认**。

还有字段级的兼容，`FoodRecord` 的 `imageUris`：

```ts
// imageUris 是后加的字段。老记录没有，构造函数已用 imageUri 初始化过
// 单元素列表；这里只在确实存了数组时覆盖它。
const stored: string[] = getStrArray(map, 'imageUris');
if (stored.length > 0) {
  r.imageUris = stored;
  r.imageUri = stored[0];
}
```

**读数据的三条原则**（本项目都在用）：

| 原则 | 做法 |
|---|---|
| **每个字段都给默认值** | `getStr(map, 'name', '未命名食物')` —— 缺了就返回 `'未命名食物'` |
| **枚举值要校验** | `toEnum(getStr(...), ALL_MEALS, MealType.LUNCH)` —— 值非法就退回默认 |
| **新字段不能让老数据崩** | 读不到就当没有，用默认值 |

```ts
// toEnum 的实现（common\JsonUtil.ets）—— 这个模式很值得学
export function toEnum<T extends string>(value: string, all: T[], defValue: T): T {
  const candidate: T = value as T;
  return all.includes(candidate) ? candidate : defValue;
}
```

**为什么需要它**：假设某天你把 `MealType` 里的 `SNACK` 删了，
但用户手机上存着 `mealType: "snack"` 的老记录。
不校验的话，这条记录会「哪一餐都不是」，在界面上凭空消失。
加了校验就退回默认餐次，记录还在。

## 七、为什么数据不上传

这是**产品决策**，但直接影响代码：

| 不上传带来的好处 | 代码上的表现 |
|---|---|
| 不需要账号系统 | 没有登录页、没有 token 管理 |
| 不需要服务器 | 没有网络请求库、没有后端代码 |
| 不会泄露 | 数据只在应用沙箱（App 私有目录，别的 App 读不到） |
| 离线可用 | 所有功能（除 AI 识别）都不需要网络 |
| 没有合规负担 | 不用写隐私政策、不用做数据导出 |

**唯一的例外**：拍照识别时把**压缩后的照片**发给**你自己配置的** AI 服务商。

关于 API Key，代码里的处理是：

```
• Key 存在本机 preferences 里（键 "ai_config"）
• 代码里 API Key 的默认值是空字符串 —— 没有任何硬编码的密钥
• 请求时直接放在 HTTP 头里发给服务商，不经过任何中间服务器
• 「我的」页有「清空全部数据」按钮，能一键抹掉
```

> **对开发者的提醒**：**永远不要把密钥写进代码**。
> 代码会进 Git、会被人看到。哪怕只是测试用的 Key，
> 一旦提交过就很难彻底删除（要改写全部 Git 历史）。
> 正确做法就是本项目这样：**让用户自己填，存在本地。**

## 八、小节：一次「记录一笔饮食」的完整数据流

把所有环节串起来，假设用户拍照识别后确认了一条「红烧肉 90克 315千卡」：

```
① 用户在结果页点「确认记录」
        ↓
② ResultConfirm 页构造一个 FoodRecord 对象
   { id: "m3k2-8a", dayKey: "2026-10-05", name: "红烧肉", grams: 90, kcal: 315, … }
        ↓
③ 调 FoodRepo.addMany([record])
        ↓
④ FoodRepo 内部：
   · loadDay("2026-10-05")  读出当天已有的记录
   · 把新记录 push 进去
   · saveDay() → Store.put("food_day_2026-10-05", JSON.stringify(列表))
   · indexSync() → 确保 "2026-10-05" 在索引里
        ↓
⑤ Store 内部：
   · putSync() 写进内存（立刻能读回来）
   · flush() 异步落盘
        ↓
⑥ 通知界面刷新（下一章讲）
```

**注意 ④ 是在「同步」执行的**——用户点确认后，数据立刻就在了，
不需要等待。这就是前面说的「同步写 + 异步落盘」带来的好处。

---

## 小结

- 数据分三类：**持久**（文件）/ **临时**（内存）/ **界面状态**（内存）
- 持久数据用 **`preferences`**（键值存储），键值都只能是简单类型
- 复杂对象要 **`JSON.stringify` 转字符串**再存
- `Store.ets` 是薄封装：**同步写内存 + 异步落盘**
- 记录「**一天一个键**」+ 一个**索引键**记录哪些天有数据
- 索引和真实数据**必须同步维护**，这是该方案的固有代价
- **新增用 `add`，改动用 `update`**，不要混
- 读老数据要**给默认值、校验枚举**，否则新老格式会打架
- **永远不要把 API Key 写进代码**
