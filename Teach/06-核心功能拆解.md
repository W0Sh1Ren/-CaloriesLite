# 06 · 核心功能拆解

前面五章讲了地基。这一章逐个看主要功能**具体怎么实现的**。

每个功能都按同一个结构讲：**它要解决什么问题 → 怎么做的 → 代码在哪 → 有什么坑**。

# 一、热量算法

## 要解决什么

「我一天该吃多少？」这个问题没有唯一答案，取决于身高体重年龄性别活动量。

## 算法链条：三层推算

```
第 1 层：BMR（基础代谢率）
   你躺着不动一天消耗多少
   男：BMR = 10×体重 + 6.25×身高 − 5×年龄 + 5
   女：BMR = 10×体重 + 6.25×身高 − 5×年龄 − 161

第 2 层：TDEE（每日总消耗）
   TDEE = BMR × 活动系数（1.2 ~ 1.9）

第 3 层：每日热量预算
   预算 = TDEE + 目标调整（减脂 −500 / 平稳减脂 −300 / 保持 0 / 增重 +300）
```

**代码在** `service\CalorieCalc.ets`：

```ts
export function calcBmr(profile: UserProfile): number {
  const weight = clamp(profile.weightKg, MIN_WEIGHT_KG, 300);
  const height = clamp(profile.heightCm, MIN_HEIGHT_CM, 250);
  const age    = clamp(profile.age, 10, MAX_AGE);

  const base = 10 * weight + 6.25 * height - 5 * age;
  const genderOffset = profile.gender === Gender.MALE ? 5 : -161;
  return Math.max(600, base + genderOffset);
}
```

## 这里有两个值得学的设计

**① 先 `clamp` 再计算**

`clamp(x, 最小, 最大)` 是把数值卡在合理范围内的函数。

**为什么**：用户可能在身高栏填了 `1880`（多打一个 0），
不卡范围的话算出来的预算会是个离谱的数字，用户会以为 App 坏了。

**输入校验的哲学**：宁可**悄悄修正**，也不要**报错拒绝**。
修正后用户看到合理结果，多打一个 0 也不会造成困扰。

**② 预算有下限，不低于 BMR**

```ts
const floor = calcBmr(profile) * FLOOR_BMR_RATIO;
return Math.round(Math.max(adjusted, floor));
```

**为什么**：如果用户选了「快速减脂」而且本身体重轻，
`TDEE − 500` 可能低于基础代谢。**长期吃不够基础代谢是有害的。**

代码层面挡住它，比在文档里写「请注意不要……」有用得多。

> 这是**「在代码里设安全边界」**的思路：
> 不指望用户理解原理，直接把不合理的路径堵死。

# 二、热量环

## 要解决什么

「今天还差多少？」——要一眼看完，不用读数字。

## 怎么做的：Canvas 手绘

**代码在** `components\CalorieRing.ets`。

**关键点**：这个环**不是**用鸿蒙的 `Progress` 组件画的，而是**用 Canvas 一笔一笔画的**。

## 为什么要自己画

`Progress` 组件有个 `Ring`（环形）模式，看起来正合适。但实测：

> `Progress` 在 Ring 模式下**不会把尺寸撑开给父容器**。
> 想要一个 210vp 的环，结果被压成 75vp 高，屏幕上只露出一小段弧。

**根因**：`Progress` 的尺寸由它自己的内部逻辑决定，
父容器问它「你要多大」时，它给的答案不对。

**解法**：用 `Canvas` 自己画 —— 你完全控制每一笔的位置和粗细。

## Canvas 带来的代价

自己画 = 自己负责重绘。而 Canvas **不在鸿蒙的属性动画通道里**。

意思是：普通的 ArkUI 组件改属性，框架会自动插值做动画。
但 Canvas 上画的弧线是「一次性画上去的路径」，改数据**不会自动重画**。

所以项目里用了两个手段：

**① `dataVersion` 版本号**

```ts
// Index.ets
@State dataVersion: number = 0;

// 每次 re读数据就自增
this.dataVersion++;
```

把这个数字传给环组件，它 `@Watch` 到变化就重新 `draw()`。

**为什么需要版本号**：如果只是「把新的数据对象传给子组件」，
子组件**收不到通知**（因为对象引用可能没变，或者自绘组件不订阅普通字段）。
显式给一个每次都变的数字最可靠。

**② 按帧插值的动画器 `ValueTicker`**

想让环的数字从 0 滚到 315，用 `animateTo` 是**无效的**：

> 实测在 `animateTo` 回调里改状态 + 手动 `draw()`，
> 拿到的是**目标值**，弧线直接瞬移。

**为什么**：`animateTo` 只插值**属性**。而 Canvas 的弧线不在属性系统里，
回调里拿到的永远是最终值。

**解法**：自己按帧推进（`common\Theme.ets` 里的 `ValueTicker`）：

```ts
this.timer = setInterval(() => {
  const elapsed = Date.now() - this.startedAt;
  const t = Math.min(1, elapsed / this.duration);
  const eased = 1 - Math.pow(1 - t, 3);        // easeOutCubic 缓动
  this.current = this.from + (this.to_ - this.from) * eased;
  apply(this.current);                          // 每帧回调，重画
  if (t >= 1) { this.stop(); }
}, 16);                                          // 约 60 帧/秒
```

**这段代码值得细看**，因为它体现了一个通用套路：

| 步骤 | 做法 |
|---|---|
| 记住起始时刻 | `startedAt = Date.now()` |
| 每帧算进度 | `t = 已过时间 / 总时长`，卡在 0~1 |
| 加缓动 | `1 - (1-t)³` —— 起步快、收尾缓 |
| 插值 | `起点 + (终点 − 起点) × 缓动后的进度` |
| 收尾 | `t >= 1` 时停掉定时器 |

**任何「框架动画做不了」的场景，都可以用这套自己实现。**

## 三个坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 忘了 `stop()` | 组件销毁后定时器还在跑，回调打到已销毁对象上 | 在 `aboutToDisappear` 里调 `stop()` |
| 用布尔值当触发信号 | 连续两次「真→真」不触发 | 用自增的数字 |
| 在 `@Builder` 里传值 | 参数只求值一次，永不更新 | 传函数 `() => value`，或改成 `@Component` |

# 三、拍照识别（最复杂的功能）

## 要解决什么

「我吃了什么、多少热量？」—— 拍照自动填。

## 完整流程

```
① 拍照 / 选图
      ↓
② 本机压缩（原图 4~8 MB → 压到长边 1024、JPEG 质量 80）
      ↓
③ 转成 base64，连同提示词发给 AI 接口
      ↓
④ AI 返回 JSON：这是什么食物、大概多少克
      ↓
⑤ ★ 先查内置食物表 ★ 命中就用表里的精确值
      ↓
⑥ 表里没有的才用 AI 的热量估算，并标注来源
      ↓
⑦ 弹结果确认页，用户可逐条修改
      ↓
⑧ 确认后才写进记录
```

## 三个关键设计

### 设计一：为什么必须先压缩

原图 4~8 MB，转成 base64 会**变大 33%**，算下来一次请求要传 5~11 MB。

后果：
- 上传慢（用户等不起）
- AI 接口通常有请求体大小限制，**直接超限被拒**
- Token 消耗按图片大小算，**费用翻好几倍**

压缩到长边 1024 后约 200 KB，**缩小 20~40 倍**，识别准确率几乎不受影响
（食物识别不需要看清纹理细节）。

**代码在** `service\ImageService.ets`。

### 设计二：为什么要先查内置食物表

AI 估算热量**误差通常在 10~20%**，因为它只能「看」份量，不知道确切成分。

而「一碗米饭 239 千卡」「100 克红烧肉 350 千卡」这种数字是**确定的**。

所以策略是：

```
AI 负责「这是什么 + 大概多少克」     ← AI 擅长的
食物表负责「每 100 克多少热量」       ← 查表更准
```

**两层的分工**，比让 AI 从头算到脚准确得多。

而且结果页会**标注来源**：

| 来源标记 | 含义 |
|---|---|
| `AI 估算` | AI 直接给的热量，误差较大 |
| 无标记 | 查表得来的，比较准 |

**让用户知道「这个数字有多可信」** —— 这比假装所有数字都一样准要诚实。

### 设计三：为什么要「确认页」这一关

如果识别完直接写进记录：

- AI 认错了（把牛肉认成猪肉），数据就被污染了
- 用户得自己去找到那条记录删掉
- **一次错误要用户做两次操作来纠正**

加了确认页，用户可以先改名字、改克重、改餐次，**确认没问题才落库**。

> **「AI 的结果不直接落库」** 是引入 AI 时的一条重要原则。
> AI 有错误率，必须给人一个复核的机会，
> 而且复核的成本要低于纠正的成本。

## 提示词怎么写的

**代码在** `service\VisionService.ets`，搜 `SYSTEM_PROMPT`。

节选几条设计：

```
3. grams 是你对这份食物克重的整数估算，针对照片中实际可见的份量，不是每100克。
4. kcal / protein / fat / carb 都是**照片中这份实际份量**的总量，不是每100克；
   热量与三大营养素要能对得上。
5. 估算时把烹饪方式算进去：同样一块肉，油炸/红烧的脂肪明显高于清蒸/水煮。
6. 如果照片里没有食物，foods 返回空数组，summary 说明原因。
7. 如果画面里有餐具或手，请借助它们推算份量大小。
```

**每条都在解决一个具体的错误模式**：

| 条款 | 防的是什么错误 |
|---|---|
| 3、4 强调「不是每 100 克」 | 模型默认爱给「每 100 克」的值，导致热量差 2~3 倍 |
| 5 提烹饪方式 | 不提醒的话模型只看食材，忽略「红烧比清蒸油多」 |
| 6 允许返回空 | 否则拍到非食物时，模型会**硬编一个食物**出来 |
| 7 用参照物 | 画面里有筷子/手时，比单纯目测准得多 |

另外要求「**只输出 JSON，不要 markdown 代码块**」：

模型很爱把 JSON 包在 ` ```json ` 里，那样解析会失败（多了解释文字）。
**在提示词里明确说清楚输出格式**，比事后写容错代码更省事。

## 一个约束：卡片和页面的差别

识别相关的代码**全在普通页面里**，桌面卡片**只显示结果**。

原因见下一节。

# 四、桌面卡片（限制最多的功能）

## 要解决什么

不打开 App，在桌面就能看到今天的热量情况。

## 关键认知：卡片不在你的 App 里运行

```
普通页面              → 跑在【你的 App 进程】里
桌面卡片              → 跑在【系统的卡片框架进程】里
```

**这个区别导致了一堆限制**，每一条都会让「习惯的写法」失效：

| 限制 | 后果 | 本项目的做法 |
|---|---|---|
| 不能长期跑定时器 | `setInterval` 会被系统冻结或回收 | 不做动画，只在数据变化时刷新 |
| **不支持 `animateTo` / `getUIContext`** | 编译期直接报错 | 卡片里不做任何动画 |
| 状态管理只能用 V1 | 不能用 `@ComponentV2` | 卡片用 `@Component` + `@LocalStorageProp` |
| **响应式追踪不追踪函数内部** | 在 getter / 辅助方法里读数据**读不到** | **所有计算在后端做完再推过来** |
| 不能用 `Button(文本)` 构造 | 文字不渲染，只剩背景色和几个白点 | 用 `Text` + 背景色模拟按钮 |
| `FormLink` 组件点击无效 | 点了没反应 | 用 `postCardAction` |

## 最重要的一条：卡片 UI 必须「零派生」

这是踩得最深的坑。原来的卡片里写：

```ts
// ❌ 这些写法在卡片里都会读不到数据
this.macroBar('蛋白', this.protein, this.proteinTarget)   // 方法内读属性
private isEmptyDay(): boolean { return this.intake <= 0; } // 方法内读属性
get primaryText() { return this.phase === 'x' ? 'A' : 'B' } // getter
```

**表现**：进度条按 0 渲染、文字为空，**而且不报错**。极难排查。

**根本原因**：卡片进程的响应式系统**不追踪函数内部对 `@LocalStorageProp` 的依赖**。
它只认「在 `build()` 里**直接**读属性」这一种形式。

**解法**：新增 `widget\CardData.ets` 作为**统一数据契约**，
所有派生（百分比、文案、配色、空状态判断）**全在后端算好**，
卡片只负责把字符串贴到界面上。

```ts
// CardData.ets：后端算好
proteinPct: string = '0%';
proteinText: string = '0 / 188 g';
proteinColor: string = '#22C55E';

// CalorieCard.ets：卡片只贴值，一个运算都没有
Text(this.proteinText)
Row().width(this.proteinPct)
```

**记住这条**：改卡片时如果发现想「顺手算一下」，那说明该往 `CardData` 里加字段了。

## 卡片的点击：不能用普通 onClick

普通页面的点击：

```ts
.onClick(() => { router.pushUrl(...) })   // ✅ 页面里可以
```

卡片里的点击**必须**用 `postCardAction`：

```ts
.onClick(() => {
  postCardAction(this, {
    action: 'router',                 // 拉起应用
    abilityName: 'EntryAbility',
    params: { cardRoute: 'camera' }   // 告诉 App 该去哪一页
  });
})
```

三种 `action`：

| action | 作用 | 本项目用在哪 |
|---|---|---|
| `router` | 拉起主应用 | 点「拍照记录」→ 进拍照页；点左边的环 → 进首页 |
| `message` | 只通知卡片后台，**不拉起应用** | 点「刷新」→ 重算数据 |
| `call` | 拉起应用的后台方法 | 没用 |

**注意**：`postCardAction` **不能链在 `@Builder` 调用后面**（返回 void），
要包一层容器再把事件绑在容器上。

## 刷新机制

| 方式 | 触发 | 说明 |
|---|---|---|
| **手动** | 点卡片「刷新」 | 发 `message` 事件给卡片后台 |
| **自动** | App 里改了记录 | 调 `reloadAllForms()`，系统广播给卡片服务 |
| **兜底** | 系统定时 | `updateDuration: 1`，每 30 分钟 |

## 一个折磨了很久的 bug

**现象**：在 App 里记完一笔，卡片点刷新**没反应**；
但过一阵再点，或者等很久，数值又对了。

**排查过程**（数据说话）：

```
一次记录后连续 7 次刷新 → records=7  intake=1880   ← 全是旧值
过了一会儿（进程重启）  → records=9  intake=2280   ← 新值
```

**关键线索**：进程号（pid）变了。

**根因**：`preferences` 在**框架层**还维护一份**进程内缓存**，
而且这份缓存**不会因为别的进程写了新值就失效**。

卡片进程是长驻的，所以它读到的永远是**启动那一刻的快照**。
所谓「过一阵自己好了」，其实是系统把卡片进程**回收重启**了，
新进程重新读文件才拿到新数据 —— **根本不是刷新生效了**。

**修法**：

```ts
static reload(context: common.Context): void {
  Store.prefs = null;
  // ↓ 关键就是这一句
  preferences.removePreferencesFromCacheSync(context, STORE_NAME);
  Store.init(context);
}
```

**为什么只置空自己的引用不够**：那是「我们这一层」的缓存，
框架那一层的还在。必须显式把实例**从框架缓存中移除**。

> **教训**：跨进程共享的存储，在长驻进程里**必须假设它有缓存**。
> 而且要查到**框架层**，不只是自己的引用。
> 区分点是「**进程有没有重启过**」——这是排查这类问题的关键线索。

# 五、饮食历史日历

## 要解决什么

「我这一周/这个月记录得怎么样？」—— 一眼看出哪些天吃超了。

## 怎么做的：月历热力图

每天一个小圆点，颜色表示当天的缺口健康程度：

| 颜色 | 含义 |
|---|---|
| 绿点 | 有缺口（吃够了但没超） |
| 浅绿点 | 基本持平 |
| 红点 | 超标 |
| 灰点 | 没记录 |

**代码在** `components\CalendarHeatmap.ets`。

## 三个实现细节

**① 数据从索引来**

日历要「哪些天有记录」，靠的是 `FoodRepo.listDays()`（第 4 章讲的索引键）。
**这就是索引存在的理由** —— 没有它就不知道要显示哪些天。

**② 换月要重算，但别只重算格子**

踩过的坑：

```ts
// ❌ 原来的写法：只重算了日历格子
private shiftMonth(delta: number): void {
  this.viewYear = y;
  this.viewMonth0 = m;
  this.cells = this.buildCells();    // ← 只更新格子
  this.monthAnimKey = ...;
}
```

结果：换月后「**本月缺口**」显示的还是上个月的数。

修法：改成走统一的 `rebuild()`：

```ts
// ✅ 走统一入口，格子和缺口一起重算
this.rebuild();
```

**教训**：一个「刷新」动作牵扯到几块数据时，
**走同一个刷新方法**，不要各自更新一部分。

**③ 滑动换月的阈值**

`PanGesture`（拖动手势）要设一个**最小位移阈值**：

```ts
const SWIPE_MIN_VP: number = 40;   // 移动超过 40vp 才算「滑动」
```

**为什么**：不设阈值的话，用户**轻轻点一下**产生的微小抖动
会被判定成滑动，日历莫名其妙就换月了。

阈值也不能太大，否则需要使劲划才有效。40vp 是试出来的手感。

# 六、体重记录与趋势曲线

## 要解决什么

「我体重在降吗？」—— 用折线图看趋势，比看一堆数字直观。

## 两个实现点

**① 曲线也是 Canvas 手绘**

原因和热量环一样（第 2 节）。代码在 `components\WeightChart.ets`。

**② 记体重会联动重算热量预算**

因为 BMR 公式里有体重：

```
BMR = 10×体重 + 6.25×身高 − 5×年龄 ± 常数
```

**体重变了，该吃多少也跟着变。** 这就是为什么记完体重，
首页的「每日预算」数字会跟着变。

**代码上怎么实现的**：`DailyService` 里有个 `effectiveProfile()`，
它会用「最近一次体重记录」覆盖「个人档案里的体重」，然后所有算法都用它：

```ts
static effectiveProfile(): UserProfile {
  // 取档案，但如果最近有体重记录，用记录里的值
}
```

**这个设计的意义**：用户不用每次称完体重都去「我的」页手动改档案。
**记一次体重，全应用的算法都跟着更新。**

# 小结

| 功能 | 核心技术 | 最大的坑 |
|---|---|---|
| 热量算法 | 三层推算 + 输入卡范围 + 预算有下限 | 无（纯计算） |
| 热量环 | **Canvas 自绘** + `ValueTicker` 按帧插值 | Canvas 不在属性动画通道里 |
| 拍照识别 | 本机压缩 → AI 识别 → **查表兜准** → 确认页 | 提示词要防具体错误模式 |
| 桌面卡片 | `CardData` 统一契约 + `postCardAction` | **卡片 UI 必须零派生**；框架级缓存 |
| 日历热力 | 索引键 + 月历格子 + 拖动阈值 | 换月要一起重算所有派生数据 |
| 体重曲线 | Canvas 手绘 + 联动重算预算 | 同热量环 |
