# 02 · 项目结构导览

这一章带你走一遍项目的每个文件夹。**读完你就知道想改东西该打开哪个文件。**

---

## 一、先看全景

```
D:\CaloriesApp\
│
├── AppScope\              ← 应用级配置（名字、图标）
├── entry\                 ← 唯一的模块，所有代码都在这
│   └── src\main\
│       ├── ets\           ★ 代码都在这
│       ├── resources\     ← 图片、文字、颜色等资源
│       └── module.json5   ← 模块配置
│
├── docs\                  ← 版本更新日志、技术报告
├── hap\                   ← 打包好的安装包（手动归档的）
├── tools\                 ← 构建脚本（正常开发用不到）
│
├── build-profile.json5    ← 构建配置（签名、编译选项）
├── oh-package.json5       ← 依赖清单（相当于 package.json）
└── README.md              ← 项目说明
```

### 「模块」是什么

上面有个 `entry` 目录，它就是一个**模块**（module）。

一个 App 可以拆成多个模块，比如：

- `entry` —— 主模块，App 的主体
- `feature-xxx` —— 按需下载的功能模块

**本项目只有一个 `entry` 模块**，因为功能少，拆开没有意义。

所有代码都在 `entry/src/main/ets/` 里 —— **记住这个路径**，后面都在这下面。

## 二、代码目录：七个文件夹各管一摊

```
entry/src/main/ets/
├── common\        地基：工具函数、全局状态、样式
├── model\         数据长什么样：类型定义、食物表
├── service\       干活：算法、存储读写、调 AI
├── components\    可复用的小界面（一个环、一行记录…）
├── pages\         完整的页面（首页、记录页…）
├── entryability\  App 入口
├── entryformability\  桌面卡片的后台服务
└── widget\        桌面卡片的界面
```

用**开餐厅**打个比方：

| 文件夹 | 相当于 | 说明 |
|---|---|---|
| `model` | **食材和菜谱的定义** | 「宫保鸡丁」这道菜由哪些材料构成 |
| `service` | **后厨** | 真正动手做菜的地方，外面看不到过程 |
| `components` | **餐具** | 盘子、碗、杯子，可反复使用 |
| `pages` | **餐桌上的一餐** | 用各种餐具装好后端给客人 |
| `common` | **水电煤、调料架** | 到处都要用的基础设施 |

**核心原则：界面（pages/components）不干重活，重活交给 service。**

为什么？因为界面代码会被反复执行（每次刷新都跑一遍），
把算法、存储读写放在里面会造成重复计算；而且界面和逻辑混在一起，
以后想改逻辑得翻界面代码，很难维护。

## 三、逐个文件夹细看

### `common\` —— 地基

| 文件 | 干什么 | 什么时候会用它 |
|---|---|---|
| `Store.ets` | **本地存储的封装** | 任何要保存数据的地方 |
| `DateUtil.ets` | 日期处理（格式化、算差值） | 处理「今天」「某一天」 |
| `JsonUtil.ets` | JSON 转换、生成唯一 ID | 存对象、新建记录 |
| `AppState.ets` | **跨页面共享状态** | 页面之间传数据 |
| `Theme.ets` | 颜色、圆角、阴影、动画时长 | 所有界面样式 |
| `SafeArea.ets` | 刘海屏 / 手势条避让 | App 启动时算一次 |
| `PermissionUtil.ets` | 申请相机、相册权限 | 点击拍照时 |
| `Material.ets` | 毛玻璃效果的参数 | 顶栏、导航栏 |

**其中最重要的是 `Store.ets` 和 `AppState.ets`**，第 4、5 章专门讲它们。

### `model\` —— 数据长什么样

| 文件 | 内容 |
|---|---|
| `Types.ets` | 所有**数据结构**的定义（一条饮食记录、一个用户档案…） |
| `Enums.ets` | 所有**固定选项**（早餐/午餐/晚餐、男/女、减脂/保持/增重…） |
| `FoodDatabase.ets` | **内置食物表**，约 290 条常见中式食物的营养值 |

**举例**：一条饮食记录在代码里长这样

```ts
// 这不是真实代码，是示意，让你先有概念
一条记录 = {
  食物名: "红烧肉",
  克重:   90,
  热量:   315,
  蛋白质: 12.6,
  脂肪:   27,
  碳水:   4.5,
  属于哪一餐: 午餐,
  日期: "2026-10-05",
  来源: "AI识别"
}
```

`Types.ets` 里就是把这个结构**正式写下来**，让全项目统一用。

> **为什么要单独一个文件定义类型？**
> 因为如果每处代码各自写一个「记录」的格式，改一个字段就要改十几个地方，
> 而且容易写错（这个文件叫 `kcal`、那个文件叫 `calories`）。
> **一处定义，处处引用** —— 这是这个项目贯穿始终的原则。

### `service\` —— 干活的地方

| 文件 | 干什么 |
|---|---|
| `CalorieCalc.ets` | **热量算法**：算基础代谢、每日预算、BMI |
| `DailyService.ets` | **每日结算**：把当天所有记录汇总成「摄入 / 缺口」 |
| `FoodRepo.ets` | 饮食记录的**读写** |
| `BodyRepo.ets` | 体重记录的读写 |
| `ExerciseRepo.ets` | 运动记录的读写 |
| `SettingsRepo.ets` | 个人档案、AI 配置的读写 |
| `FoodMatcher.ets` | 在食物表里**搜索** |
| `VisionService.ets` | **调 AI 接口**识别食物 |
| `ImageService.ets` | 图片压缩、存到本地 |

**「Repo」是 Repository（仓库）的缩写**，这类文件的职责就是
「把某一类数据存进去 / 读出来」，不掺业务逻辑。

> **为什么要分这么多 Repo？**
> 饮食、体重、运动是三类完全不同的数据，混在一个文件里会越来越乱。
> 分开后，每个文件只关心自己那类数据的存取，改一个不影响其他。

### `components\` —— 可复用的小界面

这些不是完整页面，而是**可以被反复使用的小块**：

| 文件 | 是什么 |
|---|---|
| `CalorieRing.ets` | 首页那个**热量环**（Canvas 手绘的） |
| `MacroBar.ets` | 三大营养素进度条 |
| `RecordRow.ets` | **一行饮食记录**（食物名 + 克重 + 热量 + 删除按钮） |
| `CalendarHeatmap.ets` | 记录页的**月历热力图** |
| `WeightChart.ets` | 体重**折线图**（也是 Canvas 手绘） |
| `MealFold.ets` | 餐次**展开/收起**的折叠容器 |
| `FloatingNav.ets` | 底部那个**悬浮毛玻璃导航栏** |
| `GlassTopBar.ets` | 顶部毛玻璃标题栏 |
| `RollingNumber.ets` | 数字滚动动画 |
| `ProfileOption.ets` | 「我的」页的一个选项卡片 |
| `MealGallery.ets` | 记录里的照片缩略图 |

**`components` 和 `pages` 的区别**：

- `pages` = **一整屏**，用户能「跳到」它
- `components` = **一块**，必须被 `pages` 用起来才存在

### `pages\` —— 完整的页面

| 文件 | 是哪一页 |
|---|---|
| `Index.ets` | **主页面**，包含三个页签：今天 / 记录 / 我的 |
| `HistoryTab.ets` | 「记录」页签的内容 |
| `ProfileTab.ets` | 「我的」页签的内容 |
| `Camera.ets` | 拍照识别页 |
| `ResultConfirm.ets` | 识别结果确认页 |
| `ManualAdd.ets` | 手动添加页（**目前已无入口**，保留备用） |
| `AiSettings.ets` | AI 接口配置页 |
| `DayDetail.ets` | 某一天的详情页 |

> **注意**：三个页签（今天/记录/我的）是**同一个页面 `Index.ets`** 里的三块，
> 不是三个独立页面。它们用左右滑动切换，而不是跳转。
> 这样切换更顺滑，但代价是**三个页签始终都活着**，互相通知刷新会麻烦一些
>（第 5 章讲怎么解决）。

### `entryability\` 和 `entryformability\` —— 两个入口

| 文件 | 是什么 |
|---|---|
| `entryability\EntryAbility.ets` | **App 的主入口**，负责启动窗口、加载首页 |
| `entryformability\CalorieCardAbility.ets` | **桌面卡片的后台服务**，负责给卡片准备数据 |

### `widget\` —— 桌面卡片的界面

| 文件 | 是什么 |
|---|---|
| `widget\pages\CalorieCard.ets` | 卡片长什么样（**有严格限制**，第 6 章讲） |
| `widget\CardData.ets` | 卡片的数据契约（所有计算在这里做完） |

## 四、资源和配置文件

### `entry/src/main/resources\` —— 资源

```
resources\
├── base\              默认（浅色主题）
│   ├── element\       文字、颜色 的定义
│   │   ├── string.json    ← "app_name": "轻卡记"
│   │   └── color.json
│   ├── media\         图片
│   │   ├── foreground.png  ← 图标的前景层（那个角色）
│   │   ├── background.png  ← 图标的背景层
│   │   └── startIcon.png
│   └── profile\       卡片等配置
│       └── form_config.json
├── dark\              深色主题（可选）
└── rawfile\           原样打包的文件
```

**为什么要用 `string.json` 而不是直接写中文？**

因为在代码里写 `$string:app_name`，系统会**按当前语言自动选对应的文字**。
中文系统显示「轻卡记」，英文系统可以显示别的。本项目只做了中文，
但这个机制保留着。

### 配置文件

| 文件 | 作用 | 通俗解释 |
|---|---|---|
| `AppScope\app.json5` | 应用级配置 | 这个 App **叫什么、什么图标、什么版本** |
| `entry\src\main\module.json5` | 模块配置 | 这个模块**有几个页面、需要什么权限、注册了哪些 Ability** |
| `build-profile.json5` | 构建配置 | **怎么编译、用什么签名** |
| `oh-package.json5` | 依赖清单 | **用了哪些第三方库**（本项目几乎没用） |

> **`.json5` 和 `.json` 的区别**：`.json5` 是 JSON 的宽松版，
> **允许写注释**。所以 `module.json5` 里能看到中文注释，
> 而 `form_config.json` 是严格 JSON，**不能写注释**（写了会报解析失败）。

## 五、想改东西，该打开哪个文件？

这是最实用的一节。

| 我想改… | 打开 |
|---|---|
| App 名字 | `AppScope\resources\base\element\string.json` |
| App 图标 | `docs\图标原图.png` 然后跑 `tools\make_icon.py` |
| 主题色（绿色） | `common\Theme.ets` |
| 首页热量环的样子 | `components\CalorieRing.ets` |
| 首页的布局 | `pages\Index.ets` |
| 「记录」页的内容 | `pages\HistoryTab.ets` |
| 「我的」页的内容 | `pages\ProfileTab.ets` |
| 热量计算规则 | `service\CalorieCalc.ets` |
| 内置食物表 | `model\FoodDatabase.ets` |
| 识别用的提示词 | `service\VisionService.ets`（搜 `SYSTEM_PROMPT`） |
| 桌面卡片的布局 | `widget\pages\CalorieCard.ets`（文件头有速查表） |
| 餐次选项（早/午/晚/加餐） | `model\Enums.ets` |
| 数据保存格式 | `service\*Repo.ets` + `common\Store.ets` |

## 六、`docs\` 和 `tools\` 是什么

### `docs\` —— 项目的「档案室」

```
docs\
├── 正式版1.0-更新日志.md
├── 正式版1.1-更新日志.md
├── …
├── 正式版1.7-更新日志.md          ← 每个版本改了什么、为什么改
├── 展开动画3.0.md                 ← 某个技术难点的专门记录
├── 沉浸光感1.0.md
├── HealthKit-运动健康数据读取-技术报告.md
├── 图标原图.png
└── 图标预览.png
```

**这些文档比代码更有长期价值**——代码会改，但「当时为什么这么决定」的记录不会过时。

### `tools\` —— 构建脚本

```
tools\
├── sync-src.ps1           把源码同步到编译副本
├── build.ps1              构建
├── prepare-toolchain.ps1  准备工具链
├── run-hvigor.js          构建器的补丁
├── make_icon.py           生成图标
├── make_preview.py        生成图标预览图
├── local\                 ← 工具链副本（410 MB，已 gitignore）
└── proj\                  ← 编译用的临时副本（已 gitignore）
```

> ⚠️ **正常用 DevEco Studio 开发，完全不需要碰 `tools\`。**
> 这些脚本是为了在**受限的命令行环境**里构建而写的，
> 绕开了一堆环境限制（README 里有详细说明）。
>
> ⚠️ **绝对不要删 `tools\run-hvigor.js`** —— 它是构建器的一部分，
> 删了命令行构建会直接失败。

---

## 小结

- 代码全在 `entry/src/main/ets/` 下，分七类：`common` / `model` /
  `service` / `components` / `pages` + 两个入口 + `widget`
- **界面不干重活**，算法和存储都在 `service`
- **一处定义，处处引用**（类型、颜色、文案都只定义一次）
- 三个页签是同一个页面 `Index.ets` 里的三块，不是三个页面
- `.json5` 能写注释，`.json` 不能
- `tools/` 正常开发用不到，但**不能删**
