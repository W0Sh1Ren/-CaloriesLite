## 一、术语对照

新手最容易被英文缩写绕晕，这里一次说清。

### 项目自己的概念

| 词 | 全称 / 中文 | 通俗解释 |
|---|---|---|
| **BMR** | 基础代谢率 | 你躺着不动一天消耗多少热量 |
| **TDEE** | 每日总消耗 | BMR × 活动系数，包含日常活动 |
| **缺口** | Calorie Deficit | `预算 + 运动 − 摄入`，正数=还能吃，负数=超标 |
| **预算** | 每日热量预算 | 你一天「该吃多少」的目标值 |
| **dayKey** | 日期主键 | `"2026-10-05"` 这样的字符串，全应用用它标识「一天」 |
| **餐次** | MealType | 早餐 / 午餐 / 晚餐 / 加餐 |
| **宏量营养素** | Macro | 蛋白质 / 脂肪 / 碳水，三大营养素 |

### 鸿蒙 / ArkTS 术语

| 词 | 含义 |
|---|---|
| **ArkTS** | 鸿蒙的开发语言 = TypeScript + 界面语法 |
| **.ets** | ArkTS 源文件扩展名 |
| **HAP** | 鸿蒙的安装包格式（相当于安卓的 APK） |
| **API 版本** | 开发者用的版本编号（本项目 **API 26**） |
| **Ability** | App 对外的入口（有界面的叫 UIAbility） |
| **DevEco Studio** | 华为官方的开发工具（IDE） |
| **ArkUI** | 鸿蒙的界面框架 |
| **声明式 UI** | 只描述「要什么结构」，不管「怎么搭」 |
| **Canvas** | 画布，自己一笔一笔画图形 |
| **FormKit** | 桌面卡片的开发框架 |
| **偏好存储** | `preferences`，简单的键值存储 |

### 状态装饰器（**最容易混，重点看**）

| 写法 | 数据从哪来 | 改了会刷新吗 | 什么时候用 |
|---|---|---|---|
| （无） | 组件自己的普通字段 | ❌ | 不需要驱动的值 |
| `@State` | 组件自己持有 | ✅ | **最常用**，组件自己的数据 |
| `@Prop` | 父组件传入 | ✅（单向） | 子组件接收父组件的数据 |
| `@Link` | 父组件传入 | ✅（双向） | 子组件也要改父组件（**慎用**） |
| `@Watch` | 配合上面用 | — | 值变了顺便调个方法 |
| `@Builder` | — | — | 复用一小段界面（**参数只求值一次**） |
| `@Component` | — | — | 定义一个界面组件 |
| `@LocalStorageProp` | 全局存储 | ✅ | **卡片专用** |
| `@StorageLink` | 全局存储 | ✅ | ⚠️ **本项目弃用**（键不存在会崩） |

### 布局相关

| 属性 | 含义 |
|---|---|
| `.width()` / `.height()` | 宽 / 高（`'100%'` 表示占满，数字表示 vp） |
| `.padding()` | **内**边距（自己往里缩） |
| `.margin()` | **外**边距（把自己往外推） |
| `.layoutWeight(n)` | 按比例分配**剩余**空间（不是固定尺寸！） |
| `.justifyContent()` | 主轴对齐（Column 里 = 上下） |
| `.alignItems()` | 交叉轴对齐（Column 里 = 左右） |
| `.clip(true)` | 裁掉超出容器的部分 |
| `.opacity()` | 透明度 0~1 |
| `vp` | 鸿蒙的尺寸单位，会**随屏幕密度自动缩放** |
| `sp` | 字号单位，会随**用户设置的字体大小**缩放 |

## 二、常用命令

### 构建（命令行方式）

```powershell
# ① 同步源码到编译副本（改了源码后必跑）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\sync-src.ps1

# ② 构建
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build.ps1

# 产物位置
tools\proj\entry\build\default\outputs\default\entry-default-signed.hap
```

> ⚠️ **永远不要并行跑两个构建**（会互相删文件，见坑 24）
> ⚠️ **不要删 `tools\run-hvigor.js`**（构建器的一部分）

### 安装到手机

```powershell
$hdc = 'D:\DevEco26\DevEco Studio\sdk\default\openharmony\toolchains\hdc.exe'

# 看有没有连上设备
& $hdc list targets

# 安装（-r = 覆盖安装）
& $hdc install -r 'tools\proj\entry\build\default\outputs\default\entry-default-signed.hap'

# 重启应用
& $hdc shell aa force-stop Calories.Lite.Test
& $hdc shell aa start -a EntryAbility -b Calories.Lite.Test
```

**手机要先打开「USB 调试」**（设置 → 关于手机 → 连点版本号 7 次 → 开发者选项）。

### 调试：看界面结构（**特别有用**）

```powershell
# 把当前界面的所有元素导出成 JSON
& $hdc shell uitest dumpLayout -p /data/local/tmp/p.json
& $hdc file recv /data/local/tmp/p.json 'D:\CaloriesApp\tools\p.json'
```

导出的 JSON 里每个节点有：

| 字段 | 含义 |
|---|---|
| `type` | 元素类型（Text / Column / TextInput…） |
| `text` | 显示的文字 |
| `bounds` | 位置 `[左,上][右,下]`，单位是 **px** |
| `clickable` | **能不能点** |
| `focused` | **焦点在不在它身上** ← 排查焦点问题的神器 |

**坐标换算**：这个设备 `density = 3.5`，所以 `vp = px / 3.5`。

### 调试：模拟点击 / 输入

```powershell

& $hdc shell uitest uiInput click 640 1200

# 输入文字
& $hdc shell uitest uiInput text "红烧肉"

# 滑动
& $hdc shell uitest uiInput swipe 640 1500 640 800 300
```

### 调试：看日志

```powershell
# 实时看
& $hdc shell hilog

# 只看本应用的，带上下文
& $hdc shell "hilog -x 2>/dev/null | grep -i CalorieLite | tail -30"

# 清空日志缓冲（重新测之前先清）
```

**代码里怎么打日志**：

```ts

```

> ⚠️ **必须用 `%{public}s` 而不是 `%s`** —— 不写 `public` 的话，
> 日志里的值会被打码成 `<private>`，看不到内容。

## 四、学习路线建议

如果你是从零开始，建议这个顺序：

### 第 1 周：能跑起来

| 目标 | 做什么 |
|---|---|
| 装好工具 | 装 DevEco Studio，注册华为开发者账号 |
| 跑通项目 | 打开本项目，配好签名，装到自己手机上 |
| 看懂界面 | 读 `pages\Index.ets`，对应手机上的界面找代码 |

**别急着改代码**，先建立「代码 ↔ 界面」的对应感。

### 第 2 周：能改界面

| 目标 | 做什么 |
|---|---|
| 改颜色 | 动 `common\Theme.ets` 里的颜色常量，看手机上的变化 |
| 改文案 | 找一个 `Text('...')` 改成别的内容 |
| 改尺寸 | 调 `.fontSize()` / `.height()` 这类属性 |
| 加一个元素 | 在某个 `Column` 里加一行 `Text('测试')` |

**每次改完都要重新构建 + 安装**（约 30 秒），耐心点。

> ⚠️ **改了桌面卡片要先删掉桌面上的卡片再重新添加** ——
> 卡片布局不会热更新。

### 第 3 周：理解数据流

## 五、这个项目的设计原则（改代码前想想）

改代码时如果犹豫，用这几条判断：

### 1. 界面不干重活

算法、存储读写放 `service`，界面只负责显示。
**判断标准**：如果一段代码会在每次界面刷新时重复执行，它就不该在界面里。

### 2. 一处定义，处处引用

同一个值不要在多个地方写死。
颜色写到 `Theme.ets`，类型写到 `Types.ets`，选项写到 `Enums.ets`。

**判断标准**：如果同一个数字/字符串出现了两次以上，抽出来。

### 3. 能算出来就别测量

高度、位置这类，能用公式算就算，不要指望框架告诉你。
（见坑 8）

### 4. 修问题先想「会不会挡住别人」

布局问题的修法常常引入新问题。
改之前想清楚：这个元素动位置后，会不会盖住别的？

### 5. AI 的结果不直接落库

有错误率的操作，都要给用户一个确认的机会。

### 6. 显式传递 > 就近猜测

需要跨页面/跨函数传递的信息，显式传。
任何「猜一个默认值」都会在某个场景下错。（见坑：补记日期）

### 7. 在代码里设安全边界

用户可能输入离谱的值。用 `clamp` 修正，比写文档提醒有用。

### 8. 不报错的坑最难查

**优先写「容易出错就会报错」的代码**，而不是「看起来更短」的代码。
比如用枚举代替裸字符串 —— 拼错了编译器会告诉你。

## 六、出问题时怎么办

### 排查顺序

```
① 看现象：是「不显示」「显示错」还是「点了没反应」？
        ↓
② 查第 7 章的「按症状找坑」对照表
        ↓
③ 加日志，确认数据到底对不对
   hilog.info(0x0000, 'CalorieLite', '这里: %{public}s', JSON.stringify(数据));
        ↓
④ 用 dumpLayout 看界面实际结构（bounds / clickable / focused）
        ↓
⑤ 确认「数据对但界面不对」还是「数据本身就错」
   —— 这两类的修法完全不同
        ↓
⑥ 查本机 SDK 定义，确认 API 用法
```

### 三个排查原则

**① 先确认数据，再怀疑界面**

大部分「界面不更新」其实是**数据没读到**。
加一行日志打印数据，比盯着界面猜快得多。

**② 用「进程有没有重启过」判断缓存问题**

如果「等一会就好」或者「重启就好」→ 是缓存问题。

**③ 别靠截图猜**

截图只能看到静态结果，**证明不了事件链路和焦点归属**。
用 `dumpLayout` 读 `clickable` / `focused` / `bounds`，
这些是**可验证的事实**。

> 这一条是我在这个项目里学到的最大教训。
> 我曾在「按钮点不动」上反复截图比对，浪费了很多时间；
> 后来读 `dumpLayout` 的 `focused` 属性，两次就定位了。

## 七、一页纸总结

```
【是什么】
  鸿蒙 App，API 26，ArkTS 语言，打包成 HAP

【代码在哪】
  entry/src/main/ets/
    common/     地基（存储、日期、主题、跨页状态）
    model/      数据长什么样（类型、枚举、食物表）
    service/    干活（算法、存储读写、调 AI）
    components/ 可复用界面块
    pages/      完整页面
    widget/     桌面卡片

【数据怎么走】
  界面 → Repo → Store → preferences（手机文件）
  改完 → notifyDataChanged() → 首页 reload() → 界面自动更新

【改东西先看】
  第 7 章踩坑笔记（按症状查表）

【最重要的三条】
  1. @Builder 参数只求值一次 → 要用 @Component
  2. 卡片 UI 必须零派生 → 计算放 CardData.ets
  3. 跨进程存储有缓存 → 用 removePreferencesFromCacheSync

【排错三件套】
  hilog 打日志   dumpLayout 看结构   SDK 定义查 API
```
