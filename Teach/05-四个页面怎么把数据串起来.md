# 05 · 四个页面怎么把数据串起来

这一章讲**数据流的后一半**：页面之间怎么传数据、怎么互相通知「该刷新了」。

这是新手最容易写乱的地方，也是这个项目踩坑最多的地方。

---

## 一、先看页面长什么样

很多人以为「今天 / 记录 / 我的」是三个页面。**不是。**

```
Index.ets  ← 一个页面
├── 今天（页签 1）
├── HistoryTab  ← 记录（页签 2）
└── ProfileTab  ← 我的（页签 3）
```

三个页签**同时活着**，靠左右滑动切换。

**为什么这么设计**：滑动切换比页面跳转顺滑，而且来回切不会丢状态
（比如你在「记录」页翻到了 3 月，切到「今天」再切回来，还在 3 月）。

**代价**：三个页签**一直存在**，所以：

- 它们不能靠「进入页面」这个时机来刷新数据
- 必须有一套**主动通知**的机制

除了 `Index`，还有这些**真正的独立页面**（会跳转）：

| 页面 | 从哪进 |
|---|---|
| `Camera.ets` | 首页的「拍照识别热量」按钮 |
| `ResultConfirm.ets` | 识别成功后自动进入 |
| `AiSettings.ets` | 「我的」→ AI 配置 |
| `DayDetail.ets` | 「记录」→ 点日历某一天 |
| `ManualAdd.ets` | （**目前无入口**，保留备用） |

## 二、页面之间怎么传数据

### 方式一：路由参数（本项目**没用**）

大多数框架传数据靠 URL 参数：

```ts
// 别的框架常见写法
router.pushUrl({ url: 'pages/Detail', params: { id: 123 } })
```

**本项目为什么不用**：

鸿蒙的路由参数类型是 `Object`（无类型）。在 ArkTS 这种强类型语言里，
从 `Object` 里取字段要不停做类型判断，代码会变得很啰嗦，
而且**写错字段名不会报错**，运行时才发现拿到 `undefined`。

### 方式二：全局共享状态（本项目**用了**）

把要传的数据放在一个**全局都能访问的地方**，跳转后目标页自己去取。

这个「地方」就是 `common\AppState.ets`。

### `AppState` 长什么样

```ts
export class AppState {
  /** 拍照识别完成后暂存的结果，供结果确认页读取 */
  static pending: PendingResult | null = null;

  /** 历史页是否需要刷新 */
  static needRefreshHome: boolean = false;

  /** 识别页选中的餐次，跳转前设置 */
  static targetMeal: MealType = MealType.LUNCH;

  /** 这次拍照识别要记到哪一天（空串 = 今天） */
  static targetDay: string = '';

  /** 桌面卡片带来的目标页 */
  static cardRoute: string = '';

  // …摄像头安全区尺寸、面板开关等
}
```

**关键点**：字段都是 `static`（静态）。
静态的意思是不用 `new` 就能直接用：`AppState.targetDay = '2026-10-03'`。

### 一个真实的使用流程

「从记录页给 10 月 3 日补记一笔」是怎么走通的：

```
① 用户在记录页翻到 10 月 3 日，点「补记」
        ↓
② HistoryTab 设置目标日期，然后跳转
   AppState.targetDay = '2026-10-03';
   router.pushUrl({ url: 'pages/Camera' });
        ↓
③ 拍照页不关心日期，正常拍照、识别
        ↓
④ 结果确认页保存时，**读 AppState 拿日期**
   const day = AppState.effectiveTargetDay();   // 返回 '2026-10-03'
   FoodRepo.addMany(records);                    // 记到那一天
        ↓
⑤ 结果确认页通知首页刷新，然后返回
   AppState.needRefreshHome = true;
   AppState.notifyDataChanged();
   router.back();
        ↓
⑥ 首页 onPageShow 里看到 needRefreshHome，切到那一天
   this.dayKey = AppState.effectiveTargetDay();
```

### 这里藏着一个曾经的真实 bug

`ResultConfirm` 早期写的是：

```ts
const day = todayKey();      // ❌ 写死今天
```

结果：**不管从哪天进去补记，记录都落到今天。**
用户翻到 10 月 3 日补记，数据却记到了 10 月 5 日。

修法就是引入 `AppState.targetDay`，让「要记到哪一天」显式传递。

**教训**：

> 需要「跨页面传递」的信息，**必须显式传递**。
> 任何「就近猜一个」（比如猜今天、猜当前时间）都会在某个场景下错。

### `effectiveTargetDay()` 这个小设计

```ts
/** 取本次要记录的目标日期；未设置时就是今天 */
static effectiveTargetDay(): string {
  return AppState.targetDay.length > 0 ? AppState.targetDay : todayKey();
}
```

**为什么要有它**：绝大多数情况下用户记的就是今天，只有「补记」才需要指定日期。

如果要求每处都显式设置 `targetDay`，那正常拍照流程也得记得设一次，
**忘设就记到空日期**。用「空串 = 今天」这个约定，正常流程什么都不用做。

这是很常见的设计手法：**给最常用的场景一个「默认不用管」的路径。**

## 三、怎么通知别人「数据变了」

这是本章的核心问题。

### 问题场景

用户在**结果确认页**记了一笔，然后返回首页。
首页要显示新的总摄入。但首页**不是重新创建的**（它一直在内存里），
所以它的数据还是旧的。

**怎么让首页知道该刷新？**

### 方案一：`AppStorage` + `@StorageLink`（本项目**放弃**了）

鸿蒙提供了全局的 `AppStorage`，配合 `@StorageLink` 可以双向绑定。

**为什么放弃**：踩了个大坑，代码注释里留着：

```ts
// 注意：这里不要改用 @StorageLink('dataStamp')。
// 该装饰器在绑定那一刻就要求 AppStorage 里已存在同名键，
// 而键只在首次写入时创建，冷启动会直接崩（实测进程启动即退出）。
```

**翻译**：`@StorageLink('dataStamp')` 要求 `dataStamp` 这个键**已经存在**。
但键是第一次写数据时才创建的，App 冷启动时还不存在 →
绑定失败 → **App 直接崩溃，连界面都出不来**。

而且同一个变量只能挂一个状态装饰器，也没法用 `@Watch` 兜底。

### 方案二：静态回调（本项目**采用**）

思路很简单：**谁需要刷新，谁把自己注册进去；谁改了数据，谁喊一声。**

`common\AppState.ets` 里：

```ts
export class AppState {
  /** 当日数据变更的订阅回调 */
  private static dataListener: (() => void) | null = null;

  /** 页面注册自己的刷新方法 */
  static setDataListener(fn: () => void): void {
    AppState.dataListener = fn;
  }

  /** 页面销毁时注销，避免回调指向已销毁的组件 */
  static clearDataListener(): void {
    AppState.dataListener = null;
  }

  /** 写入方在数据变动后调用 */
  static notifyDataChanged(): void {
    const fn = AppState.dataListener;
    if (fn !== null) {
      fn();          // ← 直接调用注册进来的函数
    }
  }
}
```

### 用法：两端各写一句

**接收端**（`Index.ets`，在 `aboutToAppear` 里注册）：

```ts
aboutToAppear(): void {
  AppState.setDataListener(() => {
    this.modalOpen = AppState.modalOpen;
    this.dayKey = todayKey();
    this.reload();                 // ← 重新读数据
    this.consumeCardRoute();
  });
  this.reload();
}

aboutToDisappear(): void {
  AppState.clearDataListener();    // ← 一定要注销
}
```

**发送端**（记录保存后）：

```ts
AppState.needRefreshHome = true;
AppState.notifyDataChanged();      // ← 喊一声
router.back();
```

### 为什么这个方案好

| 优点 | 说明 |
|---|---|
| **没有时序陷阱** | 不像生命周期回调那样「取决于页面栈的状态」 |
| **立刻生效** | 数据一改，接收方**当帧**就刷新，不用等用户切页面 |
| **不依赖 AppStorage** | 绕开了那个「键不存在就崩」的问题 |
| **可控** | 谁注册、谁注销，一目了然 |

### 注意「一定要注销」

```ts
aboutToDisappear(): void {
  AppState.clearDataListener();
}
```

**不注销会怎样**：回调还指向已经销毁的组件，
下次有人调 `notifyDataChanged()` 就会往一个「死掉的对象」上写数据，
可能崩溃、可能行为诡异。

> 这是**回调/订阅模式的通病**：有注册就必须有注销。
> 写这类代码时，把「注册」和「注销」写在相邻的位置，
> 形成习惯，就不容易忘。

## 四、第二条通知链路：`refreshTick`

为什么需要**两条**通知链路？因为**通知的对象不同**。

| 链路 | 谁接收 | 干什么 |
|---|---|---|
| `dataListener`（静态回调） | 只有 `Index` | 重读**当日数据**（摄入、缺口） |
| `refreshTick`（自增信号） | `HistoryTab` / `ProfileTab` | 重读**自己的数据**（体重列表、AI 配置状态） |

### `refreshTick` 怎么工作

`Index` 里：

```ts
@State refreshTick: number = 0;

onPageShow(): void {
  // 从别的页面返回时触发
  this.refreshTick++;      // ← 自增一下，就这一句
}
```

子页面里（`HistoryTab`）：

```ts
@Prop @Watch('onRefreshTick') refreshTick: number = 0;

onRefreshTick(): void {
  this.rebuild();          // ← 收到变化，重新读数据
}
```

**原理**：`refreshTick` 是个数字。父组件把它 `++`，子组件通过 `@Watch` 感知到变化，
于是重新读数据。

**为什么用「自增一个数字」而不是「传个布尔值」**：

布尔值只能表示「真/假」两种状态。如果连续通知两次，
第二次「真 → 真」**没有变化**，`@Watch` 不会触发。

而数字每次都不同（1 → 2 → 3），**每次都是变化**，每次都能触发。

> **这是个很实用的小技巧**：需要「每次都要触发」的通知，
> 用一个自增的计数器，不要用布尔值。

### ⚠️ 一条铁律：不要在 `reload()` 里改 `refreshTick`

代码注释里写着：

```ts
/**
 * refreshTick 变化时重读当日数据。
 *
 * 这条链路本身是安全的：reload() 不再回写 refreshTick，
 * 环被打断了。isReloading 只是额外兜一层，
 * 万一以后有人在 reload() 里又写了 refreshTick，也只会被挡掉而不会爆栈。
 */
```

**为什么**：`refreshTick` 变化 → 触发 `onRefreshTick` → 调 `reload()`。
如果 `reload()` 里又改了 `refreshTick` → **再次触发** → 再调 `reload()` → …

**无限循环，直接爆栈**（`RangeError: Stack overflow`）。项目里踩过。

## 五、`Index` 的 `reload()`：所有刷新的汇聚点

`Index.ets` 里这个方法是**数据刷新的唯一入口**：

```ts
private reload(): void {
  // 重入守卫：任何意外触发的嵌套调用直接返回，避免栈被撑爆
  if (this.isReloading) {
    return;
  }
  this.isReloading = true;
  try {
    this.data = DailyService.homeData(this.dayKey);   // 读当天所有数据
    AppState.mirrorToday(this.data.summary);          // 镜像一份给别处用
    this.dataVersion++;                               // 通知自绘组件重画
    this.scheduleImageMaintenance();
    AppState.refreshCard();                           // 刷新桌面卡片
  } catch (err) {
    // 记日志
  } finally {
    this.isReloading = false;
  }
}
```

几个设计点：

| 设计 | 为什么 |
|---|---|
| **`isReloading` 守卫** | 万一有嵌套调用，直接返回，不让栈无限增长 |
| **选它当唯一入口** | 拍照确认、补记、删除、运动、体重**五个入口**最终都走这里 |
| **`dataVersion++`** | Canvas 自绘组件收不到普通的数据变化通知，用版本号强制重画 |
| **`refreshCard()` 放这里** | 卡片刷新也跟着所有数据变更走，写一处覆盖全部 |
| **不改 `refreshTick`** | 避免无限循环（上面讲过） |

> **「唯一汇聚点」是个很重要的设计模式。**
> 如果每个保存成功的地方都各自写一遍刷新逻辑，那么：
> 加一个新入口时容易忘、五处逻辑可能写得不一样、出 bug 要改五处。
> 收敛到一个方法后，**改一处，全局生效**。

## 六、完整的一次数据流（把所有环节串起来）

用户在**结果确认页**记了一笔，然后返回首页：

```
【结果确认页 ResultConfirm】
  ① 用户点「确认记录」
  ② 构造 FoodRecord，调 FoodRepo.addMany(records)
     → 数据写进 preferences（第 4 章讲过）
  ③ AppState.needRefreshHome = true
  ④ AppState.notifyDataChanged()          ← 喊一声
  ⑤ router.back()                          ← 返回首页

【首页 Index】
  ⑥ notifyDataChanged 触发注册的回调
     → this.reload()
  ⑦ reload() 里：
     · DailyService.homeData(dayKey)  重新汇总当天数据
     · dataVersion++                  环重画
     · AppState.refreshCard()          桌面卡片也刷新
  ⑧ 界面自动更新（因为 data 是 @State）
```

**如果用户是从「记录」页补记的**，还多一步：

```
【记录页 HistoryTab】
  补记前：AppState.targetDay = '2026-10-03'
  补记后返回，首页 onPageShow：
     this.dayKey = AppState.effectiveTargetDay();   → 切到 10-03
     this.switchTo(0);                               → 切到「今天」页签
     this.refreshTick++;                             → 通知子页签刷新
```

## 七、给新手的三个建议

**① 跨页面数据用「全局状态 + 显式传递」**

不要靠猜、不要靠 URL 参数（强类型语言里很麻烦）。
需要传什么，就在 `AppState` 里加一个字段，跳转前赋值、目标页读取。

**② 通知用静态回调，别用框架的全局绑定**

框架的便利功能往往有隐藏的前置条件（比如 `@StorageLink` 要求键已存在）。
自己写一个十几行的回调注册机制，**行为完全可控**。

**③ 刷新逻辑收敛到一个方法**

不要让每处保存代码各自写一遍刷新。
找一个「所有数据变更都必经」的方法，把刷新逻辑放进去。

---

## 小结

- 三个页签是**同一个页面**里的三块，**始终活着**，不能靠进入页面刷新
- 跨页面传数据用 **`AppState` 的静态字段**，跳转前设、目标页读
- **必须显式传递**（比如目标日期），不要「就近猜一个」
- 通知刷新用**静态回调** `setDataListener` / `notifyDataChanged`
- 有注册就必须有**注销**（`aboutToDisappear`）
- 需要「每次都触发」的用**自增数字**，不要用布尔值
- **不要在 `reload()` 里改 `refreshTick`** —— 无限循环会爆栈
- 刷新逻辑要收敛到**唯一汇聚点**，改一处全局生效
