# 与 AI 协作找 Bug 的方法论

> 记录于正式版 1.9。这一篇不是技术文档，是**协作方式**的复盘 ——
> 因为 1.9 那个 bug 的发现过程，本身就是一次方法上的转折。

---

## 一、一句话结论

**把 AI 当"抽卡机"用，还是当"可查询的代码库"用，效率差一个数量级。**

| 用法 | 你说的话 | AI 能做的事 |
|---|---|---|
| ❌ 抽卡 | 「底部有白框，修一下」 | 只能猜。猜错了你再描述一遍，继续猜 |
| ✅ 指明方向 | 「卡片高度的参数定义在哪？起什么作用？」 | 能给出**确定的答案**，你再据此判断 |

**关键差别**：前者的输入是**现象**，后者的输入是**结构**。
现象有无数种成因，结构只有一种真相。

---

## 二、1.9 的真实过程

这个 bug 存在了很久，表现是「展开餐次明细时，底部偶尔多出一条白框」。
修复只花了很短时间，但**转折点不是修复本身，是问题的问法变了**。

### 之前：抽卡式提问（低效）

```
「明细区底部有个白框，帮我修一下」
```

AI 只能靠猜，尝试的方向包括：
- 是不是 `.padding()` 的问题？
- 是不是 `clip` 没生效？
- 是不是阴影占了布局？
- 是不是背景色分层的问题？

**每一轮都要重新描述现象、重新构建、重新装机、重新看截图。**
而且猜错的时候，现象往往"看起来"变了（其实只是换了个位置），更难判断。

### 转折：开始问结构（高效）

```
「MealFold.ets 行 98 的 .height() 和行 59-63 的 mealDetailHeight()
 这两个有什么用？」
```

这一次 AI 给出的不是猜测，而是**确定的机制说明**：

```
展开高度是算出来的，不测量：
  高度 = 上下内边距 + 条数 × 单条高度 + (条数-1) × 间距
```

接着追问：

```
「那每道菜的高度和间距的定义在哪里？」
```

答案：

```
高度：RecordRow 里没有 .height()，是内容自然撑开的
      MealFold 里的 RECORD_ROW_H = 72 是「抄」过来的观测值
间距：两处 —— Index.ets 的 Column({space:8})（真正生效）
              MealFold.ets 的 DETAIL_GAP（算高度用的副本）
```

**看到这个答案的瞬间，bug 的成因就浮出来了**：

> 算式依赖「每张卡片等高」，但卡片高度是**内容自然撑开**的，
> 而内容里有一行是**条件渲染**的 —— 前提根本不成立。

然后是一句决定性的追问（**这是整个过程的转折点**）：

```
「我发现明细区每一张卡片的高度不一定相同，
 也就是 RECORD_ROW_H 每一道卡片的高度是不同的，
 这就导致算式可能与实际对不上」
```

**这句话不是描述现象，是描述结构。** 它直接指向了根因，
剩下的只是验证和执行。

## 三、为什么"问结构"有效

### 1. 现象是发散的，结构是收敛的

| | 现象 | 结构 |
|---|---|---|
| 例子 | 「底部有白框」 | 「高度 = 条数 × 常量」 |
| 可能性 | 十几种（padding / clip / 阴影 / 背景 / 圆角 / …） | **一种** |
| 排查成本 | 每次都要构建装机看效果 | 读代码就能判断 |

**「白框」这个词本身就是陷阱** —— 它让人以为问题是"多了一个元素"，
而真相是"算出来的高度比实际内容多"。描述得再详细，也问不到点上。

### 2. AI 擅长回答"这是什么"，不擅长猜"哪里坏了"

大模型对**代码的当前状态**（某个常量是多少、某行是做什么的）
能给出可靠答案，因为这是**可验证的事实**。

但"哪里坏了"需要**对照当前状态与预期行为**，
而预期行为只有你知道（用户看到什么、期望看到什么）。

**所以分工应该是**：
```
你提供：现象 + 期望 + 结构层面的怀疑方向
AI 提供：代码事实 + 机制解释 + 修改方案
```

### 3. 你自己看逻辑时，能提供 AI 拿不到的信息

1.9 那个转折点的追问里，有一个信息是**你在手机上看到的、AI 看不到的**：

> 「我发现明细区每一张卡片的高度不一定相同」

AI 只能看到代码里 `RECORD_ROW_H = 72` 这个常量，
**看不到实际渲染出来有的高有的矮**（那时还没有真机测量）。

**这一条观察直接把「猜测」变成了「定位」。**

## 四、可复用的提问模板

从 1.9 提炼出几个问法，以后可以直接套：

### ① 定位参数
```
「X 这个值定义在哪？它起什么作用？」
```
→ 拿到**确定的机制**，而不是猜测

### ② 追依赖链
```
「这个算式依赖哪些前提？这些前提是什么保证的？」
```
→ 1.9 的关键就是问出了「依赖每张卡片等高」这个前提

### ③ 描述落差（比描述现象有用得多）
```
「代码里写的是 A，但我在手机上看到的是 B」
```
→ 直接暴露"假设与现实不符"

### ④ 问"谁在动这个值"
```
「这个变量在哪些地方被改？改动顺序是什么？」
```
→ 用于排查时序类 bug（动画打架、刷新不生效）

### ⑤ 让 AI 先给事实、再给建议
```
「先告诉我现在的逻辑是什么，不要改代码」
```
→ 避免 AI 上来就猜着改，把你带偏

## 五、反过来说：什么时候"抽卡"是合理的

不是所有场景都要先读代码。这两种情况下直接提要求更高效：

| 场景 | 例子 | 为什么可以直接说 |
|---|---|---|
| **纯主观调整** | 「颜色再深一点」「间距小一些」 | 没有对错，只有偏好；你看到效果再调最快 |
| **需求明确的新功能** | 「加一个本月缺口显示」 | 从零开始写，不存在"找 bug"的猜测成本 |

**判断标准**：

> 如果问题的答案**已经存在于代码里**（是个 bug），先问结构。
> 如果答案**还不存在**（是新需求/新偏好），直接提要求。

1.9 属于前者 —— bug 一直在代码里，只是没人问对问题。

## 六、给以后自己的三条

**① 遇到"看起来很简单但修不好"的问题，先停下来问结构**

连续两轮靠描述现象都没修好，说明方向错了。改成问：
「这个功能的参数定义在哪？依赖什么前提？」

**② 你在手机上看到的东西，一定要说出来**

AI 看不到你的屏幕。「有的卡片高有的矮」「点了没反应」
「过一会自己好了」这类观察，往往是打破猜测循环的唯一线索。

**③ 让 AI 解释，不要让它猜**

一句「先告诉我现在的逻辑」，能省掉好几轮构建装机。
**解释是免费的，构建装机不免费。**

## 七、这个项目里的正例与反例

回顾整个开发过程，两种模式都有：

| 版本 | 方式 | 结果 |
|---|---|---|
| 1.0 ~ 1.3 | 主要靠描述现象 | 能修，但每个 bug 要来回好几轮 |
| 1.4 ~ 1.5 | 开始问「这个 API 在哪、签名是什么」 | 明显变快（键盘避让、焦点问题） |
| 1.6.2 | 主动说「过一整子再点刷新，数值刷新了」 | 一句话定位到进程重启，锁定了缓存问题 |
| **1.9** | **问参数定义 → 追问依赖前提 → 自己发现矛盾** | **一轮定位** |

**1.6.2 那句「过一整子」是转折的开始** —— 那不是描述现象，
而是描述了一个**时序特征**，直接指向「缓存」这个方向。

1.9 则是完整走通了：**问结构 → 懂机制 → 自己发现前提被破坏 → 给出修复方向**。

---

## 八、最后一句

> **AI 不会因为你的要求更客气、更详细而变准；
> 它会因为你提供的信息更接近"结构"而变准。**

「底部有白框」和「卡片高度不一致导致算式失效」，
对 AI 来说是两个完全不同难度的问题 ——
**而后者是你自己能看出来的。**
