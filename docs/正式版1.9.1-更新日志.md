## 一、热量缺口改用「总消耗」计算 ★

### 问题

首页显示的缺口**比真实值偏小**，而且偏小的原因很隐蔽。

原来的公式是：

```ts
deficit = budget + exerciseKcal - intake
```

`budget` 是**每日目标**，而它已经包含了「计划要减的那部分」（例如快速减脂 −500）。
用目标去算「缺口」，等于把**计划**当成了**消耗**。

### 三个概念本来就不同，代码里混成了一个

| 概念 | 含义 | 你的数据 |
|---|---|---|
| **总消耗 TDEE** | 维持体重所需的能量 | **2628** |
| **每日目标 budget** | 今天打算吃多少 = TDEE + 目标调整，但不低于 BMR | **2190** |
| **热量缺口 deficit** | **实际**产生的能量亏空 | **942** |

**缺口是物理量**——身体实际亏了多少能量，只取决于「消耗」与「摄入」，
与「计划吃多少」无关。

如果缺口拿 `budget` 来算，会出现两种错：

1. **按计划吃的那天，缺口显示为 0** —— 但身体明明亏了 `TDEE − 目标` 那么多
2. **地板生效时**（见下），`budget` 被抬高，缺口会**比真实值更小**，
   用户会以为减脂进度比实际慢

### 修法

```ts
// DailySummary
this.deficit = tdee + exerciseKcal - intake;   // 实际缺口
this.plannedDeficit = tdee - budget;           // 计划缺口（新增，供将来对比用）
```

`DailySummary` 新增 `tdee` 字段，构造函数由 8 个参数变为 9 个。

**效果**（你的档案）：首页缺口 **504 → 942**，即 `2628 − 1686`。

## 二、BMR 安全地板会悄悄吃掉用户选的目标

### 问题

`calcDailyBudget` 有一条安全底线：**每日目标不低于 BMR**。

```ts
const adjusted = tdee + goalAdjust(profile.goal);   // 2628 − 500 = 2128
const floor    = calcBmr(profile) * FLOOR_BMR_RATIO; // 2190 × 1.0 = 2190
return Math.round(Math.max(adjusted, floor));        // → 2190
```

这条底线本身是**合理**的（不该让人把目标设得比基础代谢还低）。
但它有一个副作用：**用户选的目标被静默放弃了**。

用当前档案验证四个目标：

| 目标 | 算式 | 生效目标 | 说明 |
|---|---|---|---|
| **快速减脂** | 2628 − 500 | **2190** | ← 被地板抬回，**−500 完全没生效** |
| 减脂 | 2628 − 300 | 2328 | 正常 |
| 保持 | 2628 | 2628 | 正常 |
| 增重增肌 | 2628 + 300 | 2928 | 正常 |

用户以为自己在按 −500 执行，实际每日目标比预期高 62 千卡，
而**界面上一个字都没提示**——只会觉得「怎么减得这么慢」。

### 修法：地板生效时显式提示

`CalorieCalc` 新增三个函数，把「用户想要的」与「实际生效的」分开暴露：

```ts
budgetFloor(profile)        // 安全地板 = BMR
requestedBudget(profile)    // 目标本来会得到的值 = TDEE + 目标调整
isBudgetFloored(profile)    // 地板是否抬高了目标
```

通过 `HomeData.floorApplied` / `HomeData.requestedBudget` 传到首页，新增提示条：

> ⚠️ 所选目标会使每日目标低于基础代谢（2190 千卡），已按基础代谢计。
> 原本 2128 → 现为 2190 千卡

**这样用户能立刻看出：我选的目标没有生效，原因是安全地板。**

## 三、「基础预算」改名为「每日目标」

`CalorieRing` 里原来那一列叫「基础预算」——但它显示的是**地板抬升后的值**，
而用户会理解成「我设定的预算」。加上缺口又不是相对它算的，
**两列语义不匹配，必然引起误解**。

改名为「**每日目标**」：它是「今天该吃多少」，也是超标判定的基准线。

---

## 四、本月缺口自动变为「实际缺口」

`DailyService.monthDeficit()` 本来就是**累加每天的 `deficit`**，
所以公式一改它自动跟着变，**界面一个字没动**。

**效果**：这个数字会明显变小（甚至变负）。

以当前数据为例，本月缺口是 **−94 千卡** —— 负数是因为记录里有
「M8和牛肥牛卷 2800 千卡」这种日子，摄入超过总消耗，那天产生的是**盈余**。

> **实际缺口本来就是正负混合的。**
> 旧算法下这个数会大得多（每天都虚增了 `TDEE − 目标`），
> 看起来「减脂很顺利」，但那不是真的。

## 影响范围

`deficit` 的所有使用方**自动继承新值**，无需分别修改：

| 位置 | 显示 |
|---|---|
| 首页热量环 | 缺口数字 + 环颜色（负数变红） |
| 首页结算评语 | 「超出预算 N 千卡」/「缺口 N 千卡」 |
| 记录页日历热力图 | 每天格子的缺口与配色 |
| 记录页日详情 | 缺口 / 超出 |
| 某天详情页 | 缺口 / 超出 |
| 记录页「本月缺口」 | 合计 |

**桌面卡片未受影响**：它显示的是「还可以吃 X」= 每日目标 − 摄入，
那是**余量**而不是缺口，语义本来就是对的。
