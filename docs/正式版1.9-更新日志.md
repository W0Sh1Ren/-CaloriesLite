## 一、修掉记录卡片高度不一致 ★

### 现象

展开某一餐的明细时，**底部偶尔多出一段空白**（用户描述为「莫名其妙的白框」），
或者最后一条记录**被裁掉一截**。

### 根因：卡片不是等高的，而展开高度是「算」出来的

明细区的展开高度用的是**算术**（见 [docs/展开动画3.0.md](展开动画3.0.md)）：

```
展开高度 = 上下内边距 + 条数 × 单条高度 + (条数−1) × 间距
```

这个算式**成立的前提是「每张卡片等高」**。但 `RecordRow` 里的
三大营养素那一行是**条件渲染**的：

```ts
// 修改前
if (this.hasMacros()) {          // 三项全为 0 时整行不渲染
  Row() { 蛋白 / 脂肪 / 碳水 }
}
```

于是同一餐里会混着两种高度的卡片：

| 记录 | 内容行数 | 高度 |
|---|---|---|
| AI 识别、有营养素数据 | 3 行 | ≈ 72vp |
| 旧记录，或 AI 三项都返回 0 | 2 行 | **矮约 14vp** |

乘法一旦不成立，算出的高度就与实际不符 —— 底部多空白，或者内容被
`clip(true)` 裁掉。

> 用户的判断很准：「卡片高度不一致，会导致 `count × 高度` 的算式与实际对不上。」

### 修法：两道保险

**① 营养素行改为常显**（主要修法）

```ts
// 修改后：不再条件渲染
Row({ space: 8 }) {
  this.macro('蛋白', this.record.protein, COLOR_PROTEIN)
  this.macro('脂肪', this.record.fat, COLOR_FAT)
  this.macro('碳水', this.record.carb, COLOR_CARB)
}
```

原来隐藏它的理由是「避免出现『蛋白 0g 脂肪 0g 碳水 0g』这种误导性的空数据」，
但那样带来两个更大的问题：

- 卡片高矮不一，破坏上面的算式
- 缺数据时**整行消失**，用户读到的是「本来就没这项」，而不是「这项没记到」，
  信息反而更糊

现在常显：**0g 就是 0g，它是真实数据，不是缺失标记**；而且每张卡片天然等高。

**② 卡片高度钉死**（双保险）

`RecordRow` 新增导出常量并显式设高：

```ts
export const RECORD_ROW_FIXED_H: number = 72;

// build() 末尾
.height(RECORD_ROW_FIXED_H)
.alignItems(VerticalAlign.Center)   // 内容比固定高度矮时垂直居中
.padding({ left: 12, right: 12 })   // 上下内边距由固定高度接管
```

这样「每张卡片等高」从**靠运气吻合的观测值**变成**代码保证的事实**。
以后即使又加了条件渲染的行、或换了字体，高度仍然固定，算式不会被破坏。

### ③ 消除「两处各写一个数字」的隐患

`MealFold` 里原来自己声明了一份：

```ts
const RECORD_ROW_H: number = 72;    // 与 RecordRow 只是"碰巧相等"
```

现在改为**从 RecordRow 导入**：

```ts
import { RECORD_ROW_FIXED_H as RECORD_ROW_H } from './RecordRow';
```

高度只剩一个来源，从根上消除脱节的可能。

> 另外两个常量（`DETAIL_PAD_V` / `DETAIL_GAP`）仍须与 `Index.ets` 的
> `mealDetail()` 保持一致，**这一步没做自动化**，改样式时要留意（注释里已标明）。

### 真机验证

修完逐行测量，所有完整可见的卡片**高度完全一致**：

```
柠檬          72.0vp   蛋白 0g / 脂肪 0g / 碳水 3g     ← 三项接近全 0，也等高
M8和牛肥牛卷   72.0vp   蛋白 128g / 脂肪 240g / 碳水 0g
饮料          72.0vp
榴莲          72.0vp
蘑菇          72.0vp
虾滑          72.0vp
无糖可乐       72.0vp   蛋白 0g / 脂肪 0g / 碳水 0g     ← 全 0，也等高 ✓
```

## 二、底部导航栏玻璃质感

系统级「沉浸光感」（HDS 的 `systemMaterialEffect`）**本项目用不了**：
`@kit.UIDesignKit` 不在 OpenHarmony SDK 里（41 个 kit 全查过，没有它）。
所以改为**手工模拟**，用三处纯 ArkUI 能实现的手段：

### ① 顶缘高光带（玻璃厚度感）

画在**已有的 Canvas** 里，不新增图层（不增加合成开销）：

```ts
const g = ctx.createLinearGradient(0, 0, 0, BEVEL_BAND);
g.addColorStop(0,    'rgba(255, 255, 255, 0.95)');   // 顶缘最亮
g.addColorStop(0.45, 'rgba(255, 255, 255, 0.30)');
g.addColorStop(1,    'rgba(255, 255, 255, 0)');      // 8vp 内渐隐
```

**只在顶部画，不在底部对称画一条**——真实玻璃被光斜照时上缘接光最多、
下缘因厚度衰减而暗。对称的两条看起来像**描边**，只有上缘才像**厚度**。
它常驻，与手指在不在无关（材质属性）。

### ② 选中回弹

原来只有「按下塌陷」，抬起后直接回 1；现在加了一段越冲：

```
按下     → 0.94  塌陷
抬起     → 1.07  弹过头（180ms EaseOut）
190ms后  → 1.00  落定
```

触发时机是**在「抬起」那一刻**，不是等父组件把 `activeIndex` 传回来 ——
手指刚离开就有反馈，手感才跟得上。幅度刻意只给 7%：这是导航栏不是按钮。

## 三、页面转场统一为系统默认

之前 `DayDetail` 有自定义 `pageTransition`（新页从右滑入、旧页左移淡出），
而首页没有 —— 于是「点日历某天」和「点拍照识别 / 补记」是两种切开方式。

**转场动画是由「源页面」定义的**，所以只改目标页没用。

现在**全部页面都不写 `pageTransition`**，统一走系统默认。`DayDetail` 里
原来那段已删除，并留了注释说明：

> 以后若要恢复自定义，**涉及的所有源页面都要一起加**，否则又会分叉。
