## 修复：卡片读到的永远是旧数据

### 现象

- 应用里记完一笔，卡片**不会自动更新**
- 手动点卡片上的「刷新」，**也没反应**
- 但**过一阵再点**，或者等很久，数值又对了

### 根因：preferences 的**框架级**进程内缓存

桌面卡片进程是**长驻**的。而 `@ohos.data.preferences` 除了应用自己持有的
那个对象之外，在**框架层还维护一份进程内缓存**，这份缓存**不会**
因为别的进程（主应用）写了新值就失效。

所以卡片进程读到的始终是它启动那一刻的快照。用户看到的"过一阵自己好了"，
其实是系统把卡片进程**回收重启**、新进程重新读文件才拿到的 ——
不是刷新起了作用。

### 决定性证据

一次记录后的连续 7 次刷新 + 一次进程重启：

```
pid=49312  连续 7 次刷新   → records=7  intake=1880   ← 全是旧值
pid=49969  （进程重启后）  → records=9  intake=2280   ← 新值
```

**关键在于 pid 变了**。数据早就写进文件了（主应用读得到），
只有重启进程才能让卡片看到。

### 走过的弯路

第一版修法是只把自己的引用置空：

```ts
Store.prefs = null;        // ❌ 不够
Store.init(context);
```

日志显示 `hadCache=true ready=true`——重新打开了，**但读回来的还是旧值**。
因为框架那份缓存没动过。

### 正确修法

```ts
Store.prefs = null;
preferences.removePreferencesFromCacheSync(context, STORE_NAME);  // ← 关键
Store.init(context);
```

`removePreferencesFromCacheSync` 把 `Preferences` 实例**从框架缓存中移除**，
之后 `getPreferencesSync` 才会**重新读文件**。

抽成 `Store.reload(context)`，只有卡片进程调用它
（主应用自己是写入方，那份缓存就是最新值，没必要每个页面重开一次）。

**修复后的日志：**

```
onFormEvent: {"action":"refresh",...}
Store reload: hadCache=true ready=true
records=9  intake=2280        ← 立刻拿到新值
```

数值与应用侧完全一致（摄入 2280、碳水目标 376、蛋白目标 226）。

这个修复**同时解决了两件事**——它们本来是同一个根因：

1. 手动点刷新 → 立刻生效
2. 记录之后自动刷新（`reloadAllForms`）→ 也生效了

## 调整：三大营养素顺序

按用户指定，从上到下依次为：

```
碳水  ▓▓▓░░░░░ 144 / 376 g
蛋白  ▓▓▓▓░░░░  43 / 226 g
脂肪  ▓▓▓░░░░░  77 / 67 g
```

不是按摄入量或重要性排的，就是用户要的顺序 —— 代码注释里写明了这一点，
避免以后有人"顺手理顺"成蛋白优先。

## 保留的诊断日志

卡片侧留下几条日志，用于以后排查同类问题：

| 日志 | 含义 |
|---|---|
| `Store reload: hadCache=… ready=…` | 确认缓存是否被踢掉、存储是否可读 |
| `card build: records=N intake=X -> push intake=Y` | 读到什么、推什么 |
| `refresh pushed to <formId>` | `updateForm` 是否成功 |

`card build` 这行是这次定位问题的关键——它直接把"读到的数据"和
"推出的数据"分开打印，一眼看出是读的问题还是推的问题。

## 一枚经验

**跨进程共享的存储，在长驻进程里必须假设它有缓存。**

这次的现象很有迷惑性：数据明明写进去了、主应用读得到、`updateForm`
也返回成功，但卡片就是不更新。区分点只有一个——**进程是否重启过**。
以后遇到"改完不生效、重启就好"的跨进程数据问题，先查缓存，
而且要查到**框架层**，不只是自己的引用。
